가장 급한 사람을 찾고, 빼고, 남은 사람들에게서 다시 찾습니다.

이 단계의 생각

힙이라는 자료구조를 아직 안 쓰기로 하고, 리스트 두 개로 흉내를 냅니다. heap에는 이름을, priority_list에는 우선순위를 같은 순서로 넣습니다. 그리고 남은 사람이 있는 동안, 명단을 처음부터 훑으면서 min(priority_list)와 같은 사람을 만나면 꺼냅니다.

단계 1주석을 실행 가능한 함수로 옮긴 것
while heap:    for name, priority in patients:        if not priority_list:            break        if priority == min(priority_list):            processed.append(name)            priority_list.remove(priority)            heap.remove(name)

빨갛게 칠한 세 줄이 값을 치릅니다. min()은 남은 사람 전체를 매번 다시 훑고, remove() 두 번도 각각 리스트 전체를 훑습니다. 안쪽 for가 한 바퀴 도는 데 이미 n번씩 세 번의 순회가 겹쳐 있습니다.

바깥 while이 몇 바퀴 도는지는 입력이 정합니다

여기가 이 단계의 성격을 정하는 자리입니다. 안쪽 for는 명단을 앞에서 뒤로 훑습니다. 그러니 급한 사람이 앞쪽에 몰려 있으면 한 바퀴에 여러 명이 빠지고, 뒤쪽에 몰려 있으면 한 바퀴에 한 명씩만 빠집니다.

while을 없애려다 while로 돌아온 자리

다음 단계로 넘어가기 전에, 돌려 보지도 못하고 접은 시도가 하나 있습니다. 파일에는 [시행착오 1]이라고만 적혀 있고, 그 아래 한 줄에 철회한 이유가 남아 있습니다.

“.sort()를 쓴 이유는 결국 while 없이 우선순위를 for(1번 순회)로 정렬하려고 했던 것인데, 자연스럽게 while로 넘어가게 되어서. 사고의 전환이 필요했음.”
while (name, priority) in patients: temp = priority_list.pop() if priority == temp[-1]:
이 블록에는 측정값이 없습니다돌지 않기 때문입니다. priority_list에는 정수가 들어 있는데 temp[-1]로 인덱싱해서 TypeError: 'int' object is not subscriptable이 납니다. 그 전에 while 조건도 문제입니다. (name, priority)는 앞 반복문에서 새어 나온 값이라 루프 안에서 바뀌지 않으니, 조건이 참이면 영원히 참입니다.

그래서 이 페이지의 표에서 시행착오 1의 칸은 비어 있습니다. 실행되지 않은 코드에 초를 붙일 수는 없습니다. 다만 이 블록은 다음 단계를 낳았다는 점에서 값어치가 있습니다. “정렬을 한 번 하고 끝내고 싶다”는 생각이 여기서 처음 문장이 됐고, 단계 2가 그 문장을 코드로 옮긴 결과입니다.

이 단계의 생각

우선순위마다 (-priority, priority)라는 짝을 만들어 정렬합니다. 부호를 뒤집었으니 급한 사람이 뒤로 가고, 그러면 리스트의 pop()으로 끝에서부터 꺼낼 수 있습니다. pop()은 끝에서 빼기 때문에 remove()와 달리 리스트를 훑지 않습니다. 여기까지가 계획이었습니다.

단계 2계획과 코드가 어긋난 자리
for name, priority in patients:    priority_list.append((priority * -1, priority)) priority_list.sort()          # 시급한 것이 뒤로 옵니다 for priority_tuple in priority_list:   # 그런데 앞에서부터 훑습니다    temp = priority_tuple[-1]    for name, priority in patients:    # 이름을 찾으러 다시 전체 순회        if priority == temp:            processed.append(name)

pop()으로 끝에서 꺼내려고 부호를 뒤집어 놓고, 정작 4단계에서는 for로 앞에서부터 훑습니다. 계획은 뒤에서 꺼내는 것이었는데 코드는 앞에서 꺼냅니다.

그래서 답이 뒤집힙니다

부호를 뒤집은 채로 앞에서부터 읽으면, 가장 안 급한 사람이 첫 번째로 나옵니다. 우선순위 8인 환자가 우선순위 1인 환자보다 먼저 처리되는 순서입니다.

같은 우선순위가 있으면 사람이 불어납니다

안쪽 for는 우선순위가 같은 사람을 전부 넣습니다. 그런데 바깥 for도 같은 우선순위를 그 사람 수만큼 반복합니다. 그래서 k명이 같은 우선순위를 가지면 k × k명이 결과에 들어갑니다.

힌트가 가리킨 곳

문제 지문은 heapq를 쓰라고 했고, 파일 맨 아래에는 정석(heapq 모듈 사용) 버전이 주석으로 적혀 있습니다. 정석이라고 불렀으니 가장 좋은 답일 것 같습니다. 재 보면 그렇지 않습니다.

① 코드

03_priority_queue.py · 142-154행 (주석)돌려 보려고 오타 한 곳을 고쳤습니다
def process_emergency_room(patients):    processed = []    heap = [(priority, name) for name, priority in patients]    heapq.heapify(heap)    for _ in range(len(heap)):        # O(N log N)        item = heapq.heappop(heap)    # 원문은 heappop(hea p)        name = item[1]        processed.append(name)    return processed

튜플을 (우선순위, 이름)으로 만드는 것은 단계 3과 똑같습니다. 다른 점은 그 다음입니다. 단계 3은 sort()를 한 번 부르고 끝내지만, 여기서는 heapify로 힙을 만든 뒤 heappop을 n번 부릅니다.

부록파이썬 반복문 n바퀴
for _ in range(len(heap)):    item = heapq.heappop(heap)

.sort()는 파이썬이 아니라 C로 구현된 Timsort를 한 번 호출하고, 정렬이 끝날 때까지 파이썬으로 돌아오지 않습니다. 반면 heappop을 n번 부르는 쪽은 파이썬 반복문을 백만 바퀴 돕니다. 한 바퀴마다 함수 호출과 튜플 언패킹의 값을 치릅니다. 표기법으로는 보이지 않는 자리입니다.

전부 받아 놓고 전부 꺼내는 문제라면, 힙을 만들 이유가 없습니다. 정렬 한 번이 더 빠릅니다.

③ 그러면 힙은 왜 있나

여기부터는 문제 파일에 없는 시나리오입니다. 위 결과를 설명하려고 덧붙인 측정이며, 학습 기록의 일부가 아닙니다.

이 문제는 명단을 통째로 받아 한 번에 다 처리합니다. 실제 응급실은 그렇지 않습니다. 환자가 한 명씩 도착하고, 그때마다 “지금 가장 급한 사람이 누구인가”를 물어야 합니다. 조건을 이렇게 바꾸고 다시 재 봤습니다.

매번 다시 정렬단계 3의 방식
for name, priority in arrivals:    waiting.append((priority, name))    waiting.sort()    answers.append(waiting[0][1])
힙에 밀어 넣기부록의 방식
for name, priority in arrivals:    heapq.heappush(heap, (priority, name))    answers.append(heap[0][1])

두 방식이 내놓은 답은 모든 규모에서 완전히 같았습니다. 같은 일을 하는데 1,140배가 벌어집니다. 정렬은 한 명이 들어올 때마다 이미 정렬된 줄을 다시 정렬하지만, 힙은 새로 온 한 명을 제자리까지만 밀어 올리기 때문입니다.

전부 꺼내고 끝나는 문제라면 .sort()가 이깁니다. 들어올 때마다 지금 가장 급한 사람을 물어야 한다면 힙이 이깁니다. 힌트가 틀린 것이 아니라, 이 문제가 힙이 빛나는 모양이 아니었던 것입니다.
