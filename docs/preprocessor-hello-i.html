01

전처리기가 한 일은 이게 전부예요

#include <stdio.h>라고 적힌 자리에, stdio.h 파일의 내용을 통째로 옮겨 적었어요. 그리고 그 파일이 또 다른 파일을 부르면, 그것도 옮겨 적었어요.

hello.c — 내가 쓴 것
#include <stdio.h>

int main(void) {
    printf("Hello...");
    return 0;
}
stdio.h 외 26개 파일
typedef ... size_t;
struct _IO_FILE { ... };
extern int printf(...);
             ⋮
→
hello.i — 전처리기가 낸 것
typedef ... size_t;
struct _IO_FILE { ... };
extern int printf(...);
             ⋮
int main(void) {
    printf("Hello...");
    return 0;
}
주석은 사라졌고, #define으로 만든 이름들은 값으로 치환되어 사라졌고, #ifdef로 갈라진 길 중 선택받지 못한 쪽도 통째로 사라졌어요. 남은 것은 진짜 C 문법뿐이에요.

03

맨 위의 # 줄들은 코드가 아니에요

전처리기가 남긴 표지판이에요. "지금부터 나오는 줄은 원래 어느 파일 몇 번째 줄이었다"를 컴파일러에게 알려 줘요.

# 1 "/usr/include/stdio.h" 1 3 4
#여기가 표지판이라는 뜻이에요.
1다음 줄은 그 파일의 1번째 줄이에요.
"stdio.h"어느 파일에서 왔는지 알려 줘요.
1 3 4상황을 알리는 숫자 깃발이에요.

2
파일에서 돌아왔다
3

4

이 표지판 덕분에, 오라버니가 hello.c 4번째 줄에서 실수하면 컴파일러가 "hello.i의 841번째 줄"이 아니라 "hello.c의 4번째 줄"이라고 말해 줘요.
04

파일 하나가 27개를 데려왔어요

stdio.h는 혼자 일하지 않아요. 자기가 필요한 파일을 부르고, 그 파일이 또 다른 파일을 부르는 식으로 깊어져요. 앞부분의 표지판 행렬이 바로 이 들어갔다 나왔다의 기록이에요.

hello.c └─ stdio.h ├─ libc-header-start.h │ └─ features.h ← 이 리눅스가 무슨 기능을 켤지 결정 │ ├─ features-time64.h │ │ └─ wordsize.h ← 64비트인지 32비트인지 │ ├─ sys/cdefs.h │ └─ gnu/stubs.h ├─ stddef.h ← size_t ├─ stdarg.h ← printf의 "..." 처리용 ├─ bits/types.h ← 이름표 대량 생산 ├─ types/struct_FILE.h ← FILE의 진짜 내용물 └─ bits/floatn.h 외 …
wordsize.h는 표지판에 6번 등장해요. 여러 파일이 저마다 필요해서 불렀거든요. 그런데 이 파일 안에는 #define __WORDSIZE 64 같은 정의만 있어서, 출력에는 단 한 줄도 남기지 않아요. 표지판만 6개 남고 내용은 0줄인 이유예요.
05

남은 308줄은 네 종류뿐이에요

겉보기에 복잡하지만, 하는 일로 나누면 딱 네 덩어리예요.

80개

이름표 붙이기

typedef long unsigned int
    size_t;
typedef long int __off_t;

"이 컴퓨터에서 size_t는 사실 unsigned long이다." 기계마다 다른 크기를, 코드가 신경 쓰지 않아도 되게 이름으로 덮어 줘요.

1개

FILE 상자의 설계도

struct _IO_FILE {
  int _flags;
  char *_IO_read_ptr;
  char *_IO_buf_base;
      ⋮
};

화면에 글자를 내보낼 때 쓰는 버퍼가 여기에 들어 있어요. 지금 어디까지 썼는지, 어디까지 읽었는지를 가리키는 포인터들이에요.

3개

이미 열려 있는 통로

extern FILE *stdin;
extern FILE *stdout;
extern FILE *stderr;

키보드 입력, 화면 출력, 오류 출력. 프로그램이 시작될 때 이미 열려 있어요. printf는 이 중 stdout에 글자를 흘려보내요.

97개

함수와의 약속

extern int printf(
  const char *__format,
  ...);

printf, scanf, fopen … 이름과 인자 모양만 적혀 있고 본문이 없어요. 그래서 이 파일에는 "Hello"를 실제로 찍는 코드가 한 줄도 없어요.

06

선언은 약속이지, 실체가 아니에요

hello.i를 아무리 뒤져도 printf가 어떻게 글자를 찍는지는 나오지 않아요. 컴파일러가 알아야 할 것은 "이렇게 부르면 된다"까지거든요.

hello.i에 있는 것 — 약속

extern int printf(
    const char *__format, ...);

hello.i에 없는 것 — 실체

int printf(...) {
    /* 진짜 본문은
       libc.so 안에 있어요 */
}
__attribute__((__nothrow__)) 같은 꼬리표들도 코드가 아니에요. "이 함수는 예외를 던지지 않는다" 같은 귀띔을 GCC에게 주어서, 더 빠른 코드를 만들거나 실수를 미리 잡게 해 줘요.
07

지금 어디쯤 왔나요

전처리는 네 걸음 중 첫 걸음이에요. 아직 기계어는 한 바이트도 나오지 않았어요.

.i
전처리 — 붙여넣기 끝
지금 여기
.s
컴파일 — 어셈블리로 번역
.o
어셈블 — 기계어 조각
a.out
링크 — printf의 본문을 여기서 붙여 줌

마지막 링크 단계에서야 libc 안에 있는 printf의 진짜 본문이 내 코드와 이어져요. 05번 덩어리에서 본 "본문 없는 약속"이 그때 채워지는 거예요.

측정 환경: gcc 15, x86_64-linux-gnu, glibc 헤더. gcc -E hello.c의 실제 출력을 세어 얻은 숫자예요. 다른 컴퓨터나 다른 gcc 버전에서는 줄 수가 달라져요.
